# Техническое задание: Frontend MVP для Food Helper

**Проект:** `food_helper`  
**Раздел:** frontend + простая авторизация + история чатов  
**Версия ТЗ:** 1.0  
**Дата:** 2026-05-08  
**Статус:** готово к реализации MVP

---

## 1. Краткое описание задачи

Нужно добавить frontend-часть для проекта `food_helper`, где главный экран работает как чатовый поиск рецептов: пользователь вводит свободный текстовый запрос, получает ответ помощника и список подходящих рецептов.

Основной сценарий должен быть похож на интерфейс ChatGPT / DeepSeek / LLM-чата:

- на главной странице есть большое поле ввода;
- пользователь задает вопрос обычным языком;
- после отправки запроса экран превращается в чат;
- ответы backend отображаются как сообщения ассистента;
- найденные рецепты отображаются карточками под ответом;
- авторизованные пользователи видят историю своих чатов;
- неавторизованные пользователи могут пользоваться чатом, но не видят историю.

Для MVP авторизация должна быть простой: **email + пароль**.

---

## 2. Текущее состояние проекта

На момент подготовки ТЗ проект уже содержит backend/API для рецептов:

- FastAPI-приложение в директории `app/`;
- PostgreSQL + `pgvector` для рецептов и эмбеддингов;
- гибридный поиск: vector search + keyword search;
- основной чатовый endpoint `POST /v1/chat`;
- endpoint получения рецепта `GET /v1/recipes/{recipe_id}`;
- debug endpoint `POST /v1/search/debug`;
- таблицы `chat_sessions`, `chat_messages`, `conversation_state` в SQL-схеме.

В текущем виде backend уже поддерживает `conversation_id` в `ChatRequest`, а `ChatResponse` возвращает `conversation_id`, `answer`, `recipes`, `selected_recipe`, `nutrition`, `substitutions`, `sources`, `requires_clarification` и другие поля.

Главная недостающая часть для пользовательской истории: в `chat_sessions` пока нет привязки к пользователю. Поэтому для MVP нужно добавить таблицу пользователей и поле `user_id` в таблицу chat-сессий.

---

## 3. Цели MVP

### 3.1. Продуктовые цели

1. Сделать главный экран приложения в формате чатового поиска рецептов.
2. Дать пользователю возможность искать рецепты естественным языком.
3. Отображать ответы backend удобно: текст ответа + карточки рецептов + детали рецепта + КБЖУ + замены ингредиентов.
4. Добавить простую регистрацию и вход по email/password.
5. Показывать историю чатов только авторизованным пользователям.
6. Не показывать и не восстанавливать историю для гостей.

### 3.2. Технические цели

1. Добавить frontend-приложение в репозиторий, желательно в директорию `web/`.
2. Интегрировать frontend с существующим `POST /v1/chat`.
3. Добавить backend endpoints для авторизации.
4. Добавить backend endpoints для истории чатов.
5. Обеспечить разграничение доступа: пользователь может видеть только свои чаты.
6. Сохранить текущие backend-сценарии поиска, уточнений, КБЖУ и замен ингредиентов.

---

## 4. Не входит в MVP

В MVP не нужно делать:

- OAuth через Google/GitHub/Yandex;
- подтверждение email;
- восстановление пароля;
- роли пользователей;
- админ-панель;
- оплату/тарифы;
- шаринг чатов по публичной ссылке;
- совместные чаты;
- streaming-ответы токенами;
- голосовой ввод;
- загрузку фото еды;
- сохранение истории для гостей;
- перенос гостевого чата в аккаунт после регистрации.

Эти пункты можно добавить позже в backlog.

## 5. Пользовательские роли

### 5.1. Гость

Гость — пользователь, который не вошел в аккаунт.

Гость может:

- открыть главную страницу;
- отправить сообщение в чат;
- получить ответ и рецепты;
- продолжать текущий чат, пока страница не обновлена;
- открыть карточку рецепта из текущего ответа;
- перейти на страницу логина или регистрации.

Гость не может:

- видеть список прошлых чатов;
- открывать старые чаты;
- сохранять историю;
- восстанавливать чат после перезагрузки страницы.

### 5.2. Авторизованный пользователь

Авторизованный пользователь может:

- войти по email/password;
- выйти из аккаунта;
- отправлять сообщения в чат;
- создавать новый чат;
- видеть список своих чатов;
- открывать предыдущий чат;
- продолжать предыдущий чат;
- переименовывать чат;
- удалять чат;
- видеть только свои чаты.

---

## 6. Основные пользовательские сценарии

### 6.1. Гость открывает главную страницу

**Шаги:**

1. Пользователь открывает `/`.
2. Frontend проверяет `GET /v1/auth/me`.
3. Если пользователь не авторизован, frontend показывает гостевой режим.
4. На экране отображается большое поле ввода и кнопки “Войти” / “Зарегистрироваться”.
5. Сайдбар истории не отображается.

**Ожидаемый результат:**

Гость видит чатовый поиск, но не видит историю.

---

### 6.2. Гость отправляет первый запрос

**Пример запроса:**

```text
Посоветуй легкий ужин с курицей без грибов
```

**Шаги:**

1. Пользователь вводит текст.
2. Frontend добавляет сообщение пользователя в локальное состояние React.
3. Frontend отправляет запрос:

```http
POST /v1/chat
```

```json
{
  "message": "Посоветуй легкий ужин с курицей без грибов",
  "options": {
    "top_k": 5
  }
}
```

4. Backend возвращает `conversation_id`, `answer`, `recipes` и другие поля.
5. Frontend сохраняет `conversation_id` только в оперативном состоянии страницы.
6. Frontend отображает ответ ассистента и карточки рецептов.

**Ожидаемый результат:**

Пользователь видит чатовый ответ и список рецептов. История не появляется.

---

### 6.3. Гость продолжает текущий чат

**Пример запроса:**

```text
Расскажи подробнее про первый рецепт
```

**Шаги:**

1. Frontend отправляет следующий запрос с `conversation_id`, полученным ранее:

```json
{
  "conversation_id": "uuid-текущего-чата",
  "message": "Расскажи подробнее про первый рецепт",
  "options": {
    "top_k": 3
  }
}
```

2. Backend использует контекст текущего диалога.
3. Frontend отображает новый ответ.

**Ожидаемый результат:**

Гость может продолжать текущий диалог, пока не обновил страницу.

---

### 6.4. Гость обновляет страницу

**Шаги:**

1. Гость ведет чат.
2. Гость нажимает refresh в браузере.
3. Frontend загружается заново.
4. `conversation_id` и сообщения не берутся из `localStorage` / `sessionStorage`.
5. Экран снова показывает стартовое состояние.

**Ожидаемый результат:**

Гость не видит старый чат. История не восстановлена.

---

### 6.5. Пользователь регистрируется

**Шаги:**

1. Пользователь открывает `/register`.
2. Вводит email и пароль.
3. Frontend отправляет:

```http
POST /v1/auth/register
```

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

4. Backend создает пользователя, хеширует пароль и устанавливает auth cookie.
5. Frontend переводит пользователя на `/`.
6. Пользователь видит интерфейс авторизованного режима.

**Ожидаемый результат:**

Пользователь зарегистрирован и вошел в систему.

---

### 6.6. Пользователь входит в аккаунт

**Шаги:**

1. Пользователь открывает `/login`.
2. Вводит email и пароль.
3. Frontend отправляет:

```http
POST /v1/auth/login
```

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

4. Backend проверяет пароль и устанавливает auth cookie.
5. Frontend загружает профиль через `GET /v1/auth/me`.
6. Frontend загружает список чатов через `GET /v1/chats`.

**Ожидаемый результат:**

Пользователь видит главный чат и сайдбар истории.

---

### 6.7. Авторизованный пользователь создает новый чат

**Шаги:**

1. Пользователь нажимает “Новый чат”.
2. Frontend очищает активные сообщения.
3. Пользователь отправляет первый запрос.
4. Frontend вызывает `POST /v1/chat`.
5. Backend создает `chat_session` с `user_id` текущего пользователя.
6. Backend сохраняет сообщения пользователя и ассистента.
7. Frontend обновляет список истории.

**Ожидаемый результат:**

Новый чат появляется в истории пользователя.

---

### 6.8. Авторизованный пользователь открывает старый чат

**Шаги:**

1. Пользователь кликает на чат в сайдбаре.
2. Frontend переходит на `/chat/{conversation_id}` или обновляет активный чат на текущей странице.
3. Frontend вызывает:

```http
GET /v1/chats/{conversation_id}
```

4. Backend проверяет, что чат принадлежит текущему пользователю.
5. Backend возвращает сообщения.
6. Frontend отображает историю диалога.

**Ожидаемый результат:**

Пользователь видит выбранный чат и может его продолжить.

---

### 6.9. Авторизованный пользователь удаляет чат

**Шаги:**

1. Пользователь открывает меню чата в сайдбаре.
2. Нажимает “Удалить”.
3. Frontend показывает подтверждение.
4. Frontend вызывает:

```http
DELETE /v1/chats/{conversation_id}
```

5. Backend проверяет владельца и удаляет чат.
6. Frontend убирает чат из сайдбара.

**Ожидаемый результат:**

Чат удален только у текущего пользователя.

---

## 7. UX/UI требования

## 7.1. Общий стиль

Интерфейс должен ощущаться как современный LLM-чат:

- чистый экран;
- фокус на поле ввода;
- сообщения в виде диалога;
- минимальное количество лишних кнопок;
- быстрый переход к новому чату;
- удобная история слева для авторизованного пользователя;
- адаптивность под desktop и mobile.

---

## 7.2. Главная страница `/`

### Для гостя

На странице должны быть:

- логотип или название `Food Helper`;
- краткий подзаголовок, например: “Подберу рецепт по ингредиентам, ограничениям и целям”; 
- большое поле ввода по центру;
- кнопка отправки;
- примеры быстрых запросов;
- кнопки “Войти” и “Зарегистрироваться”; 
- отсутствие истории чатов.

Примеры быстрых запросов:

```text
Легкий ужин с курицей без грибов
Завтрак без молока до 300 ккал
Чем заменить сахар в выпечке?
Что приготовить из творога и банана?
```

### Для авторизованного пользователя

На странице должны быть:

- левый сайдбар с историей чатов;
- кнопка “Новый чат”;
- центральная область активного чата;
- поле ввода снизу;
- меню профиля или кнопка выхода;
- возможность открыть прошлый чат.

---

## 7.3. Состояние “первый экран до отправки сообщения”

До первого сообщения центральная область должна показывать:

- приветствие;
- поле ввода;
- 3–6 примеров запросов;
- легкий акцент на том, что можно писать естественным языком.

Пример текста:

```text
Что приготовить сегодня?
Напишите, какие продукты есть дома, что нельзя есть или какую цель хотите учесть.
```

---

## 7.4. Состояние активного чата

После отправки сообщения экран должен показывать:

- сообщение пользователя;
- loading state ответа ассистента;
- сообщение ассистента;
- карточки рецептов, если backend вернул `recipes`;
- блок уточняющего вопроса, если backend вернул `requires_clarification = true`;
- блок замен ингредиентов, если backend вернул `substitutions`;
- блок КБЖУ, если backend вернул `nutrition`;
- ссылки на источники, если backend вернул `sources`.

---

## 7.5. Поле ввода

Поле ввода должно:

- быть многострочным textarea;
- поддерживать отправку по `Enter`;
- поддерживать перенос строки по `Shift + Enter`;
- блокироваться во время отправки запроса;
- иметь кнопку отправки;
- показывать ошибку, если сообщение пустое;
- учитывать backend-лимит `MAX_MESSAGE_CHARS`, для MVP — 1000 символов.

Поведение:

- пустое сообщение не отправляется;
- при ошибке API введенный текст не должен пропадать;
- после успешной отправки поле очищается;
- пока идет ответ, повторная отправка блокируется.

---

## 7.6. Карточка рецепта

Карточка рецепта должна отображать поля из `RecipeCard`:

- название;
- краткое описание, если есть;
- калории;
- белки/жиры/углеводы, если есть;
- количество порций, если есть;
- время приготовления, если есть;
- сложность, если есть;
- аллергены, если есть;
- ссылку “Подробнее”.

Минимальная структура карточки:

```text
Название рецепта
Описание
КБЖУ: 320 ккал · Б 25 г · Ж 12 г · У 30 г
Порции: 2 · Время: 30 мин · Сложность: средняя
[Подробнее]
```

---

## 7.7. Детальная карточка рецепта

При клике на “Подробнее” frontend должен получить детали:

```http
GET /v1/recipes/{recipe_id}
```

Детали можно показывать одним из двух способов:

1. В модальном окне.
2. На отдельной странице `/recipes/{recipe_id}`.

Для MVP предпочтительно модальное окно, потому что оно быстрее реализуется и не требует отдельной навигационной логики.

В деталях показывать:

- название;
- описание;
- ингредиенты;
- шаги приготовления;
- КБЖУ;
- порции;
- свойства рецепта;
- ссылку на исходный рецепт.

---

## 7.8. Уточняющий вопрос

Если backend вернул:

```json
{
  "requires_clarification": true,
  "clarification": {
    "question": "...",
    "options": ["..."]
  }
}
```

Frontend должен:

- показать вопрос ассистента;
- показать варианты ответа кнопками, если они есть;
- при клике на вариант отправить его как следующее сообщение пользователя в тот же `conversation_id`.

---

## 7.9. Сайдбар истории

Сайдбар показывается только авторизованному пользователю.

Сайдбар должен содержать:

- кнопку “Новый чат”;
- список чатов;
- название каждого чата;
- дату/время последнего обновления;
- активное состояние выбранного чата;
- меню действий: переименовать, удалить;
- empty state, если истории еще нет.

Сайдбар не должен рендериться для гостя.

---

## 7.10. Mobile UI

На мобильных устройствах:

- сайдбар скрывается;
- история открывается кнопкой в header;
- поле ввода закреплено внизу;
- карточки рецептов идут вертикально;
- модальное окно рецепта занимает почти весь экран;
- кнопки логина/регистрации доступны в верхнем меню.

## 8. Frontend стек

Рекомендуемый стек для MVP:

```text
Next.js
TypeScript
Tailwind CSS
TanStack Query
Zustand
React Hook Form
Zod
```

### Почему Next.js

Next.js удобен для этого проекта, потому что в будущем могут появиться:

- отдельные страницы рецептов;
- публичные страницы рецептов;
- SSR/metadata;
- роутинг `/chat/{conversation_id}`;
- layouts для гостевого и авторизованного режима;
- удобный деплой отдельного frontend-приложения.

### Почему TanStack Query

TanStack Query нужен для:

- загрузки `GET /v1/auth/me`;
- загрузки `GET /v1/chats`;
- загрузки `GET /v1/chats/{conversation_id}`;
- invalidation списка чатов после отправки сообщения, удаления или переименования;
- обработки loading/error states.

### Почему Zustand

Zustand можно использовать для локального состояния активного чата:

- текущие сообщения гостя;
- текущий `conversation_id` гостя;
- активный чат авторизованного пользователя;
- состояние открытого модального окна рецепта.

Важно: для гостя сообщения и `conversation_id` не сохранять в persisted storage.

## 10. Frontend routing

### `/`

Главная страница.

Поведение:

- если пользователь не авторизован — гостевой чат без истории;
- если пользователь авторизован — чат с сайдбаром истории;
- при первом сообщении создается/получается `conversation_id`.

### `/login`

Страница входа.

Поля:

- email;
- пароль.

После успешного входа:

- redirect на `/`.

### `/register`

Страница регистрации.

Поля:

- email;
- пароль;
- повтор пароля.

После успешной регистрации:

- автоматический вход;
- redirect на `/`.

### `/chat/[conversationId]`

Страница конкретного чата для авторизованного пользователя.

Поведение:

- если пользователь не авторизован — redirect на `/login`;
- если чат не принадлежит пользователю — показать ошибку `404` или `403`;
- если чат найден — отобразить сообщения и разрешить продолжение диалога.

## 11. Frontend state management

### 11.1. Гостевой режим

Для гостя хранить только в памяти:

```ts
{
  conversationId: string | null;
  messages: ChatUiMessage[];
  isSending: boolean;
}
```

Запрещено для гостя:

- сохранять `messages` в `localStorage`;
- сохранять `conversationId` в `localStorage`;
- загружать `GET /v1/chats`;
- показывать ссылку на конкретный `/chat/{conversation_id}` как историю.

После refresh все гостевые сообщения должны исчезнуть.

### 11.2. Авторизованный режим

Для авторизованного пользователя:

- профиль загружается через `GET /v1/auth/me`;
- список чатов загружается через `GET /v1/chats`;
- активный чат загружается через `GET /v1/chats/{conversation_id}`;
- после нового сообщения список чатов обновляется;
- после удаления чата список чатов обновляется.

## 12.2. Обновление `chat_sessions`

Нужно добавить привязку сессии к пользователю и название чата.

```sql
ALTER TABLE chat_sessions
ADD COLUMN IF NOT EXISTS user_id UUID REFERENCES users(id) ON DELETE CASCADE;

ALTER TABLE chat_sessions
ADD COLUMN IF NOT EXISTS title TEXT;

CREATE INDEX IF NOT EXISTS chat_sessions_user_updated_idx
```

Правила:

## 12.4. Password hashing

Пароли нельзя хранить в открытом виде.

Для MVP использовать один из вариантов:

- `passlib[bcrypt]`;
- `pwdlib`;
- `argon2-cffi`.

Минимальные требования:

- пароль хешируется перед сохранением;
- при логине сравнивается хеш;
- пароль не возвращается в API;
- email нормализуется: trim + lowercase.

## 15. Обновление `POST /v1/chat`

Текущий `POST /v1/chat` нужно расширить так, чтобы он учитывал авторизованного пользователя.

### 15.1. Request остается совместимым

```json
{
  "conversation_id": "uuid или null",
  "message": "Посоветуй легкий ужин с курицей без грибов",
  "options": {
    "top_k": 5,
    "include_debug": false
  }
}
```

### 15.2. Поведение для гостя

Если пользователь не авторизован:

- запрос разрешен;
- новый чат создается с `user_id = NULL`;
- `conversation_id` возвращается в ответе;
- frontend хранит `conversation_id` только в памяти;
- история через `GET /v1/chats` недоступна;
- после refresh чат не восстанавливается.

### 15.3. Поведение для авторизованного пользователя

Если пользователь авторизован:

- новый чат создается с `user_id = current_user.id`;
- существующий чат можно продолжить только если он принадлежит `current_user.id`;
- если пользователь передал `conversation_id` чужого чата, backend возвращает `404`;
- после ответа обновляется `chat_sessions.updated_at`;
- если у чата нет `title`, title создается из первого сообщения пользователя.

### 15.4. Автоматический title

Для MVP title можно генерировать без LLM:

```text
title = первые 40–60 символов первого сообщения пользователя
```

Пример:

```text
Посоветуй легкий ужин с курицей без грибов
```

Title:

```text
Легкий ужин с курицей без грибов
```

Если сообщение длинное, обрезать и добавить `…`.

## 21. Security requirements

1. Пароли хранить только в виде хеша.
2. Auth token хранить в `HttpOnly` cookie, не в `localStorage`.
3. Все endpoints истории должны требовать авторизацию.
4. Пользователь не может получить чат другого пользователя.
5. `GET /v1/chats/{conversation_id}` должен возвращать `404` для чужого чата.
6. `PATCH` и `DELETE` должны проверять владельца чата.
7. Гостям нельзя отдавать список чатов.
8. Для production cookie должен быть `Secure=true`.
9. Email перед сохранением нормализуется.
10. Ответы API не должны возвращать `password_hash`.

## 23. Acceptance criteria

MVP считается готовым, если выполняются все условия ниже.

### 23.1. Гостевой режим

- пользователь может открыть `/` без логина;
- пользователь может отправить запрос в чат;
- пользователь получает ответ и карточки рецептов;
- сайдбар истории не отображается;
- после refresh сообщения гостя исчезают;
- frontend не сохраняет гостевые сообщения в `localStorage`;
- frontend не сохраняет гостевой `conversation_id` в `localStorage`.

### 23.2. Авторизация

- пользователь может зарегистрироваться по email/password;
- пользователь может войти по email/password;
- пользователь может выйти;
- после входа frontend понимает, что пользователь авторизован;
- после logout история скрывается.

### 23.3. История чатов

- авторизованный пользователь видит список своих чатов;
- новый чат появляется в истории;
- старый чат можно открыть;
- старый чат можно продолжить;
- чат можно переименовать;
- чат можно удалить;
- пользователь не видит чужие чаты.

### 23.4. Интеграция с текущим backend

- `POST /v1/chat` работает из frontend;
- `GET /v1/recipes/{recipe_id}` работает из frontend;
- ответы с `recipes` корректно отображаются карточками;
- ответы с `selected_recipe` отображают детали рецепта;
- ответы с `nutrition` отображают КБЖУ;
- ответы с `substitutions` отображают замены;
- ответы с `requires_clarification` отображают уточняющий вопрос.

### 23.5. Безопасность

- пароли не хранятся открытым текстом;
- auth cookie `HttpOnly`;
- history endpoints требуют авторизацию;
- ownership проверяется на backend;
- чужой `conversation_id` не раскрывает данные.

### Авторизованный пользователь

1. Зарегистрироваться.
2. Отправить первый запрос.
3. Убедиться, что чат появился в истории.
4. Нажать “Новый чат”.
5. Создать второй чат.
6. Открыть первый чат из сайдбара.
7. Продолжить первый чат.
8. Переименовать чат.
9. Удалить чат.
10. Выйти из аккаунта.
11. Убедиться, что история скрылась.

### Безопасность

1. Создать пользователя A и пользователя B.
2. Создать чат от пользователя A.
3. Попробовать открыть этот чат от пользователя B.
4. Ожидаемо: `404` или ошибка доступа.
5. Попробовать продолжить чужой чат через `POST /v1/chat`.
6. Ожидаемо: `404` или ошибка доступа.

## 27. Итоговое решение

Для MVP принимается следующая логика:

1. Главная страница становится чатовым поиском рецептов.
2. Гость может пользоваться чатом, но не видит и не восстанавливает историю.
3. Авторизованный пользователь получает историю чатов.
4. Авторизация простая: email + пароль.
5. Гостевой чат не переносится в аккаунт после регистрации.
6. Backend должен привязывать chat sessions к `user_id` только для авторизованных пользователей.
7. Frontend должен хранить гостевой чат только в оперативном состоянии страницы.
8. Все endpoints истории должны быть защищены авторизацией и ownership checks.
