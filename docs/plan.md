# План: RAG по рецептам (food_helper)

## Цель

Собрать систему, где пользователь задаёт вопрос на естественном языке, а ответ строится с опорой на каталог рецептов: при необходимости подтягивается контекст из базы (релевантные рецепты и поля), иначе ответ идёт без привязки к выдаче поиска. Идея описана в `README.md`: RAG, решение «нужен ли контекст из БД» — через оркестрацию и/или LLM.

## Структура каталогов (ориентир по фазам)

| Каталог | Роль |
|---------|------|
| `db/` | Схема Postgres, pgvector, миграции (фаза 0) |
| `docker/` | `Dockerfile` loader и `Dockerfile.embed` |
| `pipeline/` | Сбор каталога с сайта → JSONL (до БД) |
| `data/` | Справочные JSON (категории и т.п.) |
| `scripts/ingest/` | Загрузка JSONL в Postgres |
| `scripts/embedding/` | Эмбеддинги в `recipe_embeddings`, проверки |
| `scripts/search/` | Офлайн поиск по `embeddings.json` (фаза 1 — перенос в SQL/API) |
| `docs/` | План, документация |

## Уже есть в репозитории

- **Postgres + pgvector**: `docker-compose.yaml` (сервис `db`, образ `pgvector/pgvector:pg16`).
- **Схема рел + JSONB**: `db/init/01_schema.sql` — таблица `recipes` (поля рецепта, `ingredients` / `steps` / `raw` и др. в JSONB).
- **Загрузка данных**: `scripts/ingest/load_jsonl_to_postgres.py` + профиль `loader` в `docker-compose.yaml`.
- **Эмбеддинги и поиск (офлайн)**: `scripts/embedding/embed_recipes.py`, `scripts/search/search_recipes.py`; при необходимости JSON с векторами — в т.ч. `archive/embeddings.json` — векторный поиск в БД сейчас в `recipe_embeddings`, JSON остаётся для отладки/офлайн.

Ниже этапы — доработка и сборка поверх этого, а не «с нуля только таблицы».

## Пошаговый план

### Фаза 0. База данных и векторы

1. Доработать модель хранения векторов: либо колонка `embedding vector(...)` в `recipes`, либо отдельная таблица (например `recipe_embeddings` с FK на `recipes`). Файлы: `db/init/01_schema.sql`, при смене схемы — учёт volume Postgres в Docker.
2. Связать пайплайн эмбеддингов с БД: обновление/дозапись векторов после загрузки или отдельным job (затронуты `scripts/embedding/embed_recipes.py`, при необходимости `scripts/ingest/load_jsonl_to_postgres.py`).
3. Контроль целостности: соответствие записей в БД и векторов (каждый вектор ссылается на существующий рецепт).

### Фаза 1. Поиск (топ-K и обогащение из SQL)

1. Нормализация запроса пользователя для поиска: русский текст, выделение значимых токенов/фраз (без «мусорных» слов по возможности) — затем по ним строится запрос к векторному поиску.
2. Векторный поиск: топ **10** рецептов по сходству с запросом (как в исходном п. 4.2).
3. Обогащение: по идентификаторам найденных рецептов — выборка полного контекста из реляционной части + JSONB в `recipes` (SQL / один запрос с `IN` / JOIN при отдельной таблице эмбеддингов).

Задействованные артефакты: `scripts/search/search_recipes.py` (логику переносим/дублируем в сервисе), `db/init/01_schema.sql`, доступ к БД из будущего API.

### Фаза 2. LangChain и обёртки промптов

**Зачем LangChain:** цепочки RAG, маршрутизация «нужен ли поиск / контекст из БД», сборка промпта из шаблонов, при необходимости — память диалога в следующих итерациях.

1. Изучить минимально необходимый кусок LangChain: RAG pipeline, `Runnable`, разделение веток.
2. Разработать текстовые шаблоны (системный + пользовательский контекст):
   - ветка **с БД**: в промпт попадают выбранные поля рецептов (топ-K);
   - ветка **без БД**: общий ответ без вставки выдачи поиска (идею «две обёртки» проверить на реальных формулировках запросов).
3. Зафиксировать контракт: что именно передаётся в LLM (сырой JSON фрагмент vs краткая выжимка).

### Фаза 3. API

1. **Эндпоинт запроса пользователя** — принимает сообщение, возвращает ответ (и при необходимости метаданные: использован ли поиск, id рецептов). Внутри: нормализация → поиск → сборка промпта → вызов LLM.
2. **Опционально** — отдельный внутренний/отладочный эндпоинт «сырой поиск» (топ-K + фрагменты из БД) без генерации ответа моделью.
3. Единый формат ошибок и валидация входа (пустой запрос, слишком длинный текст, таймауты).

### Фаза 4. Метрики и выбор LLM (сначала критерии, потом сравнение)

1. **Сценарии для оценки** (под них же метрики): ответ с подобранными рецептами из БД; уточнение по ингредиентам/шагам; вопрос «как изменить рецепт» (см. фазу 5).
2. **Метрики**: релевантность ответа контексту, галлюцинации, латентность, стоимость, качество русского, достаточная длина контекста под размер выдачи топ-10.
3. **Выбор модели**: провайдер с web-playground или ручная вставка промпта на сайте провайдера — сравнить кандидатов по сценариям из п. 1.

### Фаза 5. Вызовы LLM по сценариям (бывш. п. 7)

1. **7.1 — Ответ с рецептами из БД:** после поиска и SQL-обогащения — промпт с контекстом рецептов → LLM формирует ответ пользователю (кратко, со ссылками на `recipe_url` по желанию).
2. **7.2 — Изменение рецепта:** пользователь спрашивает, как изменить рецепт (замены ингредиентов, диета, порции). В промпт передаётся исходный рецепт из контекста; в плане приёмки зафиксировать: ответ либо **явно помечен как предложение**, либо не противоречит исходным шагам/ингредиентам (выбрать одну политику и придерживаться её в промпте и БФТ).

### Фаза 6. Прототип веб-приложения

Поле ввода запроса, отображение ответа, индикация загрузки; опционально блок «источники» со ссылками `recipe_url` для топ-K.

### Фаза 7. Стабилизация

Поиск багов, доработка фронта, регрессия по разделу БФТ ниже.

## БФТ (базовые / бизнес-функциональные тесты)

Чек-лист приёмки. По мере выполнения можно отмечать `- [x]`.

### Данные

- [ ] Загрузка JSONL в Postgres завершается без ошибки на тестовом наборе.
- [ ] Уникальность `recipe_url` соблюдается (конфликты обрабатываются предсказуемо: skip / upsert — как зафиксируешь в коде).
- [ ] JSONB поля читаются приложением без падений при типичных записях.

### Поиск

- [ ] На фиксированном запросе и модели эмбеддингов возвращается ровно K кандидатов (K ≤ 10, если в каталоге достаточно рецептов).
- [ ] После векторного поиска SQL-обогащение возвращает те же рецепты, что и id из поиска (нет «битых» ссылок на строки).
- [ ] Нормализация запроса не ломает кириллицу и осмысленные фразы.

### API

- [ ] Пустой или слишком длинный ввод — корректный HTTP-код и сообщение об ошибке.
- [ ] Таймаут вызова LLM не вешает воркер без ответа клиенту (ошибка/504 по политике).

### RAG

- [ ] В ветке с поиском ответ использует переданный в промпт контекст (spot-check по 2–3 заранее известным рецептам в контексте).
- [ ] При пустом или нерелевантном поиске — осмысленный fallback: честное «в каталоге не нашёл» + общий совет **без** выдуманных рецептов (или другая зафиксированная политика — главное, единообразие).

### Сценарий «изменить рецепт»

- [ ] Ответ соответствует выбранной политике (см. фаза 5 п. 2): пометка «предложение» или согласованность с исходными шагами.

### UI

- [ ] Отправка сообщения и отображение ответа.
- [ ] Ошибка сети / 5xx от API показывается пользователю понятным текстом.
